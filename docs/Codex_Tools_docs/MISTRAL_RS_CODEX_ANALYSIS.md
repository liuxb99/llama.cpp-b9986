## 1. Does mistral.rs actually work with Codex CLI?

**Partially yes — but only for `function_call` tools.**

- The [codex_config.toml](examples/server/codex_config.toml) configures `wire_api = "responses"` and is documented in the official docs at `docs/src/content/docs/guides/serve/coding-agents.md`.
- The owner (EricLBuehler) has a `codex` label on the repo and submits PRs **generated by Codex CLI** (e.g., #1428, #1429, #1435).
- A draft PR #1344 ("Experiments with mistralrs-codex") exists but is **never merged**.
- **However**, the Responses API only supports `function_call` output items. It does **not** support:
  - `custom_tool_call` (no `OutputItem::CustomToolCall` variant)
  - `custom_tool_call_output` (no input item variant)
  - `tool_search_call` (no variant)
  - `web_search_call` (no variant)
  - `namespace` (no flattening logic)

Since Codex CLI **requires** `custom_tool_call` for tools like `apply_patch`, mistral.rs **cannot** serve the full Codex workflow. Basic `function`-type tools (e.g., `shell_command`, `update_plan`) do work because they map to `function_call` output items.

## 4. Comparison: llama.cpp b9986 vs mistral.rs

| Dimension | llama.cpp b9986 | mistral.rs |
|-----------|----------------|------------|
| **Request conversion** | `oai_to_chatcmpl()` in `server-chat.cpp` — handles all input item types, tool_map building, developer merge | `convert_input_items_to_messages()` in `responses.rs` — handles fewer types, no tool_map |
| **Tool output history** | `append_tool_output_message()` supports `function_call_output`, `custom_tool_call_output`, etc. | Only `FunctionCallOutput` — no `CustomToolCallOutput` |
| **Tool parser** | `parse_normalized_tool_calls()` + `parse_xml_tool_call_fallback()` — XML fallback for models that don't use PEG grammar | Relies entirely on Chat Completions tool calling (PEG grammar in mistralrs-core) |
| **Response item builder** | `restore_responses_tool_call()` + `restore_tool_call_from_original()` — supports function/custom/namespace/tool_search/web_search | `chat_response_to_response_resource()` — only maps to `OutputItem::FunctionCall` |
| **Custom tool support** | ✅ Full support via `build_responses_tool_map()` with `original_type: "custom"` | ❌ No support |
| **Namespace flattening** | ✅ `build_responses_tool_map()` flattens namespace sub-tools with composite keys | ❌ No support |
| **Tool search** | ✅ Output restoration for `tool_search_call` | ❌ No support |
| **Web search** | ✅ Output restoration for `web_search_call` + replacement mode | ❌ Only via Chat Completions path |
| **Streaming events** | Complete set with `sequence_number`, `output_index`, `content_index`, `item_id` | Complete set with same fields |
| **SSE `item_id` field** | ✅ Present on content/tool events | ❌ Not present — uses `call_id` instead of `item_id` for function_call events |
| **History restore** | `set_tool_call_ids()` + `restore_responses_tool_call()` | Direct mapping from ChatCompletionResponse |
| **Output restore** | `restore_tool_call_from_original()` — protocol-preserving passthrough | `chat_response_to_response_resource()` — hardcoded mapping |
| **Call ID** | `call_` + tool_call.id — stable across rounds | Built from LLM output — stable across rounds |
| **Status** | `completed`, `incomplete` with `incomplete_details` | `completed`, `incomplete`, `failed`, `cancelled` |
| **Tools in prompt** | Explicitly erased (`tool_schema=0`, `grammar=0`) | Passed through to Chat Completions (standard behavior) |
| **Build system** | C++ / CMake / MSVC | Rust / Cargo |

## 5. What Can Be Directly Backported to llama.cpp

| Source (mistral.rs) | Function | Target (llama.cpp) | Portability | Notes |
|---------------------|----------|-------------------|-------------|-------|
| `responses_types/events.rs` | `StreamingEvent` enum design | `server-task.cpp` SSE builder | **Pattern only** — Rust→C++ translation needed | The Rust enum-based approach with serde tags is cleaner than C++ manual JSON construction |
| `responses_types/items.rs` | `OutputItem::FunctionCall` format | `server-task.cpp` `restore_tool_call_from_original()` function_call branch | **Already covered** — llama.cpp already has this | llama.cpp's function_call format is identical |
| `responses_types/resource.rs` | `ResponseResource` builder pattern | `build_oai_resp_metadata()` | **Already covered** | llama.cpp already builds full response objects |
| `responses.rs:123-298` | `convert_input_items_to_messages()` | `oai_to_chatcmpl()` | **Already covered** — comparable breadth | Both handle message, function_call, function_call_output |
| `cached_responses.rs` | Response caching (GET/DELETE) | `server-task.cpp` | **Portable pattern** | Rust trait → C++ abstract class. llama.cpp currently doesn't cache Responses. |
| `responses.rs:855-990` | `OpenResponsesStreamer` streaming implementation | `to_json_oaicompat_resp_stream()` | **Already covered** | Both emit the same event sequence |
| `responses_types/enums.rs` | `ItemStatus`, `ResponseStatus` enum design | `server-task.cpp` status strings | **Minor pattern** | llama.cpp uses raw strings; enum would be cleaner |

### Key Finding: No Direct Code to Port

The analysis shows **zero functions that could be directly copy-pasted** between the two codebases:

- **Language barrier**: mistral.rs is Rust; llama.cpp is C++. Every function would need manual translation.
- **Different internal representations**: mistral.rs uses `OutputItem` enum + serde; llama.cpp uses `common_chat_msg` struct + nlohmann::ordered_json.
- **Different tool-calling pipeline**: mistral.rs reuses Chat Completions tool calling; llama.cpp has a separate Responses bridge with XML fallback.
- **What llama.cpp already has**: llama.cpp's `restore_responses_tool_call()`, `build_responses_tool_map()`, and streaming SSE already match or exceed mistral.rs's Responses API support.

### The One Worthwhile Pattern

The `StreamingEvent` Rust enum design (tagged union with serde) is architecturally cleaner than llama.cpp's ad-hoc JSON construction. But converting it to C++ would be a large refactor with no functional gain — the existing C++ code already produces identical SSE output.

## 6. If mistral.rs Can Run Codex CLI — Why?

mistral.rs **can** run Codex CLI for **basic function-only workflows** because:

1. **Full SSE event sequence**: It emits all required events (`response.created` → `response.completed`) with correct `sequence_number`, `output_index`, and `content_index`.

2. **Correct `function_call` format**: The `OutputItem::FunctionCall` variant produces:
   ```json
   {"type":"function_call","id":"fc_...","call_id":"call_...","name":"...","arguments":"..."}
   ```
   which matches what Codex CLI expects for function-type tools.

3. **Function_call_output round-trip**: Input items of type `function_call_output` are correctly converted to tool-role messages with matching `call_id`.

4. **Codex config documented**: The `codex_config.toml` and official docs make it trivial to connect.

5. **Owner uses Codex**: EricLBuehler actively uses Codex CLI (many PRs are Codex-generated), ensuring dogfooding.

### Why It Fails for Full Codex Workflow

Codex CLI requires **custom tool calls** (`apply_patch`, etc.). These are `"type": "custom"` tools that produce `"type": "custom_tool_call"` output items with `input` instead of `arguments`. mistral.rs has **no `OutputItem::CustomToolCall` variant** — the `OutputItem` enum only has `Message`, `FunctionCall`, `ShellCall`, and `ShellCallOutput`.

This means:
- Codex's `apply_patch` tool (a `custom`-type tool) cannot be represented
- Codex's `namespace` tools (for MCP connectors) cannot be flattened
- Codex's `tool_search` and `web_search` tools are not supported at the Responses level

## 7. Answers to Specific Questions

### 1. Is mistral.rs truly connected to Codex CLI?
**Partially.** The `codex_config.toml` example exists, docs document it, and the owner uses Codex CLI for development. However, the Responses API only supports `function_call` — not `custom_tool_call`. Basic function-type tools work; `apply_patch` and MCP connectors do not.

### 2. Does it fully support Responses API?
**No.** The Responses API implementation supports the full event stream (SSE) and `function_call`/`function_call_output` for input/output, but **lacks**:
- `custom_tool_call` / `custom_tool_call_output`
- `tool_search_call` / `tool_search_output`
- `web_search_call`
- `namespace` flattening

### 3. Does it support custom tool?
**No.** The `OutputItem` enum (`responses_types/items.rs:309-352`) has no `CustomToolCall` variant. The `TaggedInputItem` enum (`items.rs:95-123`) has no `CustomToolCallOutput` variant.

### 4. Does it support namespace?
**No.** There is no namespace flattening logic anywhere in the codebase. The `ToolType` enum only has `Function` variant.

### 5. Does it support tool_search?
**No.** No `tool_search_call` output item or `tool_search_output` input item exists.

### 6. What code is most worth porting?
**Nothing is directly portable** (Rust→C++ barrier, different architectures). But the following patterns/designs are worth studying:
- `StreamingEvent` enum with serde tags (cleaner than ad-hoc JSON)
- `ResponseResource` builder pattern with `with_*` methods
- `ResponseCache` trait for optional GET/DELETE support
